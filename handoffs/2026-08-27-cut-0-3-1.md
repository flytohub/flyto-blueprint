# Cut 0.3.1 to PyPI

- Date: 2026-08-27
- Owner: claude
- Branch: `claude/record-0-3-1`
- Status: Active

## What shipped

`flyto-blueprint` 0.3.1 is on PyPI. One change: the `core` extra's floor rose
to `flyto-core>=2.31.1` for GHSA-wmwj-g59x-c8px (critical) — `verify.spec`
reached past the module allowlist and the dangerous-permission gate to execute
arbitrary host commands. 2.31.0 is affected.

## Why it was cut when it was

Not on this package's own schedule. `flyto-ai` raised its Blueprint floor to
`>=0.3.1` in the same chain, and its CI could not resolve a version that did
not exist:

```
ERROR: Could not find a version that satisfies the requirement
flyto-blueprint>=0.3.1; extra == "dev"
```

The floor and the release are one act. A floor naming an unpublished version is
not a stricter floor — it is an uninstallable package.

## Verified

- `python3 -m pytest -q` on `main` at the tagged commit: 398 passed.
- `scripts/check_release_drift.py`: PASS, `0.3.1 is unreleased; no v0.3.1 tag`,
  run before tagging. This is the check that exists because 0.2.2 sat on PyPI
  while `main` carried unreleased changes.
- Publish workflow on tag `v0.3.1`: completed success (Trusted Publishing).
- **The artifact, not the source.** Installed `flyto-blueprint==0.3.1` from PyPI
  into a clean venv with `--no-deps` and read its metadata:

  ```
  installed: 0.3.1
  flyto-core>=2.31.1; extra == 'core'
  ```

  Source and wheel can carry the same version and differ; what a consumer
  resolves is the wheel's `Requires-Dist`, so that is what was asserted.

## Not verified

- No runtime behaviour was exercised against a real `flyto-core` 2.31.1
  install. This release changes a declaration, not code — `flyto_blueprint`
  imports no Core module — but that is a reason the check was skipped, not a
  claim that it passed.
- The 0.3.0 handoff's open items are unchanged; nothing here addresses them.

## Note for whoever is next

0.3.0 was pushed directly to `main`, bypassing branch protection, and was not
reverted because 0.3.0 was already on PyPI pointing at it. That is recorded in
`2026-08-26-cut-0-3-0.md`. 0.3.1 went through a pull request (#21) and was
merged normally; the protection is intact.
